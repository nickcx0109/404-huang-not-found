# 網頁版效能規劃

上一版（prototype v0.5）在筆電上會卡。這份文件整理卡的原因、新版要先定好的效能規則，以及要不要另外架 server。

## 1. 先講結論：架 server 解決不了卡頓

卡頓是每一幀的畫面算不完，工作都在玩家自己的瀏覽器和顯示卡上。把素材放到 server 只會讓「載入」變快，進遊戲之後的 FPS 不會變。

| 方案 | 能改善什麼 | 不能改善什麼 | 建議 |
|---|---|---|---|
| 素材放靜態網站或 CDN（GitHub Pages、Cloudflare Pages） | 第一次載入時間、多人同時下載 | 遊戲中的 FPS | 要做，幾乎免費 |
| 遊戲邏輯搬到 server（殭屍 AI、命中判定由 server 算） | Host 那台筆電的 CPU 負擔 | 每個人自己的畫面繪製 | 先不做，等量測出來真的是 Host CPU 卡再說 |
| 雲端渲染、串流畫面 | 理論上什麼都行 | 延遲高、要 GPU 主機、課程專題做不起來 | 不做 |

所以重點放在「讓每一幀變便宜」，server 維持現在的做法：只轉送訊息的 relay（`server.mjs`），外加一個放素材的靜態網站。

## 2. 上一版為什麼卡（讀程式碼的推估，還要實測確認）

| 項目 | 上一版的做法 | 為什麼貴 |
|---|---|---|
| 殭屍 | 每隻約 12 個 mesh（身體、四肢分開），最多同時 64 隻，全部會投影 | 光殭屍就約 770 次 draw call，陰影再畫一次，約 1,500 次。筆電大約 300 次就開始吃力 |
| 解析度 | `devicePixelRatio` 最高到 2 | 筆電常是 1.5 倍縮放，要算的像素是 1080p 的 2.25 倍 |
| 後製 | 4 倍 MSAA 的 HalfFloat 畫面＋6 層 bloom＋最後一道合成 | 對內顯來說很重，而且和解析度一起放大 |
| 陰影 | 2048 的 PCF 軟陰影，跟著玩家移動 | 每幀把會投影的東西再畫一遍 |
| 點光源 | 場景約 7 盞，加上槍口光、電弧光 | Three.js 是 forward rendering，每多一盞燈，每個有打光的像素都要多算一次 |
| Host 的 CPU | Host 一個人算所有殭屍的尋路、移動、命中 | 殭屍多時 JavaScript 主執行緒會塞住 |

## 3. 新版的效能規則（開工就照做，不要事後補救）

### 3.1 預算

目標：一般筆電（內顯）1080p 維持 60 fps，最差不低於 45 fps。

| 項目 | 上限 |
|---|---|
| Draw call | 300 |
| 畫面上的三角面 | 50 萬 |
| 同時開的動態燈 | 4 盞（含手電筒）；其餘用自發光材質假裝 |
| 投影的燈 | 1 盞 |
| 單章素材下載量 | 15 MB |
| 同時存在的殭屍 | 依品質等級：低 24、中 40、高 64 |

### 3.2 做法

1. **殭屍改成一隻一個 mesh 加骨架動畫**（SkinnedMesh），或用 InstancedMesh 一次畫一大群。一隻殭屍從 12 次 draw call 降到 1 次，這是效果最大的一項。殭屍在 `web/js/enemies/`，改之前先看 [GAMEPLAY.md](GAMEPLAY.md) 的敵人契約。
2. **靜態場景合併**：同一種材質的場景物件在載入時合併成一個 mesh；重複出現的東西（樹、護欄、桶子）用 InstancedMesh。上一版 `GFX.Builder` 已經會合併單一道具，新版改成合併整個區塊。
3. **霧也是效能工具**：新版本來就要濃霧（視距 20～30 m），相機遠平面跟著霧拉近，霧後面的東西不畫。第一章的路切成幾段，只載入目前這段和前後一段。
4. **陰影只給近處**：只有手電筒投影，範圍 15 m 以內；遠處和小東西不投影。
5. **解析度上限 1.0～1.5**，不用 `devicePixelRatio` 2。
6. **後製簡化**：MSAA 改成 FXAA 或關掉，bloom 從 6 層減到 3～4 層，用半解析度算。
7. **殭屍分距離更新**：遠處和看不到的殭屍降低 AI 和動畫的更新頻率（例如每 3 幀一次）。
8. **尋路搬到 Web Worker**：flow field 的計算不放在主執行緒，Host 的畫面才不會被拖慢。
9. **素材格式**：GLB 用 Draco 或 Mesh Optimizer 壓縮，貼圖用 KTX2；能用頂點色就不用貼圖。

### 3.3 品質等級

設定選單提供 低／中／高 三檔，第一次進遊戲先跑 3 秒自動選檔：

| 項目 | 低 | 中 | 高 |
|---|---|---|---|
| 解析度倍率 | 0.75 | 1.0 | 1.5 |
| 陰影 | 關 | 手電筒 1024 | 手電筒 2048 |
| 後製 | 只有暗角和顆粒 | 加 bloom（3 層） | 加 bloom（4 層）＋色差 |
| 最多殭屍數 | 24 | 40 | 64 |
| 霧中粒子 | 關 | 少 | 多 |

遊戲中如果連續 2 秒低於 45 fps，自動先降解析度倍率，再降一檔。

## 4. 量測：先量再優化

1. **效能面板**：網址加 `?perf=1` 時顯示 FPS、每幀毫秒數、draw call、三角面、燈數、殭屍數（Three.js 的 `renderer.info` 就有這些數字）。
2. **固定測試場景**：一個腳本把相機放在固定位置、生 40 隻殭屍、跑 20 秒，記錄平均和最差的幀時間。每次改美術或殭屍都跑一次，數字寫進 PR 說明。
3. **用卡過的那台筆電測**：上一版在哪台筆電卡，就用那台當基準機。先用 `?perf=1` 量一次上一版，確認上面第 2 節的推估哪幾項是真的。

## 5. 和美術流程的關係

[SCENE_PIPELINE.md](../art/SCENE_PIPELINE.md) 的面數和檔案大小上限就是照這份預算訂的。新增兩條驗收：

- 每章場景完成時，在固定測試場景的 FPS 要符合第 3.1 節的目標。
- Fable 擺完場景後回報 draw call 和三角面數，超過預算就先合併或改用 InstancedMesh，再交回來。

## 6. 執行順序

1. 用 `?perf=1` 量上一版，在基準筆電上找出真正的瓶頸（半天）。
2. 新版一開始就做好：品質等級、解析度上限、效能面板、固定測試場景。
3. 殭屍改成單一 mesh 加骨架動畫（和敵人模組的人一起做）。
4. 場景合併、InstancedMesh、分段載入，跟著每一章的美術一起做。
5. 素材部署到靜態網站，relay server 照舊。
